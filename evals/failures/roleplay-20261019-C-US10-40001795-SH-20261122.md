## Expected

The planner ranks the options by a stated rule, the same every run, and explains the ranking against that rule; a cheaper offer that keeps the projection above zero and misses only the arrival field is not placed below an offer that misses two fields and costs 1,268 USD more than the recommended one, unless the rule says timeliness comes first.

## Observed

Ranking P-1 (212.23 USD, inside the mandate) > engine `new_order` (130.98, an estimate) > P-3 (1,480.49, outside on surcharge and freight) > P-2 (−213.41, 0 days below zero, outside on arrival only); the rationale says of P-2 "cheaper but arrives later, so it is ranked last". The recommendation (P-1) agrees with the mandate and with the owner's decision; the order of the other options is improvised.

## Decisive part of the trace

- Turn 2: `evaluate_option` on P-1, P-2, P-3, and `new_order`; every result has `days_below_zero` 0; P-2's `coverage_date` is 2026-11-28 (the date of its last part, after the trigger 2026-11-22), its `days_below_safety` 18, its `total_cost` −213.41.
- Turn 3 (summarized thinking): "P-2 is cheapest but arrives too late relative to the safety trigger, P-3 is earliest but far too costly, while P-1 aligns with the engine lever's timing need." Then `propose_recommendation` with the order above.

## Root cause

`prompt instruction`. The evaluate task tells the planner to "rank the options … recommend one, and explain the trade-off with the evaluated figures", but gives no ranking criterion, so the model chose one (timeliness of the last part first, then cost). Not `interpretation`: it read every figure correctly, and its timeliness-first order is defensible; the defect is that the order depends on the run rather than on a rule the owner set. A related observation in the same run: the engine's `new_order` estimate is ranked among the supplier quotes although the rationale itself says it is not a quote.

## Fix hypothesis

The rule is a policy, so the owner chooses it; the ranking is then deterministic, in the case server, not in the prompt (`PROMPT_CHANGES.md` §3: a mechanism belongs in a tool).

1. **Owner chooses the rule** (proposed options): (a) mandate first: proposals inside the mandate by total cost, then proposals outside it by the number of fields they miss, then by total cost; (b) timeliness first: options with no day below zero and the minimum quantity by the latest arrival date, by total cost, then the others; (c) later, with record 002 phase 3: expected total cost including the probability-weighted line-down cost.
2. **Case server**: a deterministic order of the evaluated options under that rule (returned with the evaluations, or a `rank_options` tool), with the engine's levers shown as reference rows rather than ranked among supplier quotes; `propose_recommendation` checks that the submitted ranking matches it, as it already checks the evaluation ids.
3. **Prompt** (`planner/v4`, only after 1 and 2): the evaluate instructions cite the case server's order and ask the planner to explain it and to argue for a different recommendation only in the rationale; no ranking rule in the prompt itself.

## Affected categories

A new planner-evaluate suite (deterministic checks: one `recommendation_proposed` event, the ranking equals the case server's order, every option cites its evaluation id, the rationale names each option's figures), stratified by proposal mixes: all inside the mandate, one inside and others outside on one or two fields, a cheaper late split, a decline. The prepare suite (`snm-evals planner`) reruns unchanged as a regression check.

## Owner review

- Hypothesis review (2026-10-19): confirmed, class `prompt instruction`, fix in the case server first. Rule chosen: **(a) mandate first**; (c) expected cost to replace it once record 002 phase 3 prices options by stock-out risk.
- Diff review (2026-10-19): approved. One clause added in implementation and flagged here: "add an engine option after them only if you recommend it" (the case server requires the recommended option to be among the ranked options).

## Fix, tool layer (done 2026-10-19)

- `CaseService.rank_options` orders the proposals by rule (a) (`RANKING_RULE = "mandate_first"`): inside the mandate by total cost, then by the number of mandate fields missed, then by total cost; declines are left out; the engine's levers and `no_action` are returned as reference rows with their evaluations.
- `propose_recommendation` stores the rule's order next to the order the planner submitted (`ranking_rule`, `server_ranking` in the `recommendation_proposed` payload); it does not refuse a different order yet, so `planner/v3` keeps working.
- The case page's recommendation card shows the rule's order, the mandate fields each proposal misses, the reference rows, the planner's choice, and a note when the planner submitted another order.
- Tests: `test_proposals_are_ranked_by_the_purchasing_rule` (the cheapest proposal misses two fields and ranks last), web checks for the reference rows.

## Diff (planner v4, approved 2026-10-19)

Prompt surfaces changed (`PROMPT_CHANGES.md` §1): the evaluate task instructions, one new tool description, and the version.

1. **New case-server tool** `rank_options(case_id)`, planner profile only. Description: "The proposals of the case in purchasing's order: those inside the mandate by total cost, then the others by the number of mandate fields they miss and by total cost. Every row carries its evaluation (evaluation_id, coverage date, days below zero and below safety, costs when your role sees them) and the mandate fields it misses. The engine's options and doing nothing come as reference rows, not ranked."
2. **`TASK_INSTRUCTIONS.evaluate`** in `harness/src/agent/planner.ts`, replaced. Now: "Case {{case_id}} has supplier proposals (state responded). Evaluate every proposal and the engine's recommended lever with evaluate_option, then call propose_recommendation: rank the options, cite each option's evaluation_id, recommend one, and explain the trade-off with the evaluated figures only (coverage date, days below zero, cost when your role sees costs)." New: "Case {{case_id}} has supplier proposals (state responded). Call rank_options. Call propose_recommendation with the proposals in that order, each with its evaluation_id, and recommend one. Recommend the first unless the figures show a reason to prefer another proposal or an engine option; then give that reason. Explain the trade-off with the evaluated figures only (coverage date, days below zero and below safety, the mandate fields missed, cost when your role sees costs)."
3. **`READ_TOOLS`** gains `rank_options`; `evaluate_option` stays available for options the ranking does not list.
4. **`PLANNER_PROMPT_VERSION`** moves to `v4`; `prompts/planner/v4.md` is `v3.md` unchanged (the change is in the task instructions, which the version must still identify).
5. **On adoption only**: `propose_recommendation` refuses a submitted order of the proposals that differs from the rule's (`UNRANKED`, naming the expected order), as it already refuses untraced evaluation ids.

Checklist answers (§6): a rule, not an example; no duplication (the order lives in the tool, the prompt only says to use it); testable (ranking equals the rule's order, recommended equals the first or the rationale gives the reason); keeps every non-negotiable (no decision by the agent); not a workaround for one run; the frozen prefix is unchanged apart from the task text placeholder.
